## Implemented in this checkout

- **Identity and role routing:** Auth0 OIDC Authorization Code flow with PKCE, `state`/`nonce` validation, verified ID tokens and opaque PostgreSQL-backed sessions. Customer and professional memberships are separate. Professional access starts pending; operator membership is never granted from the login request.
- **Request isolation:** `account_workspaces` stores separate customer requests. A customer can keep multiple requests; an assigned professional can load and act on multiple jobs. State, booking, evidence and PayPal API calls use the workspace ID and server-verified ownership. Migration 005 copies existing account state; migration 006 removes the old single-state tables.
- **Catalog and directory:** professionals submit an account-bound service profile, Amsterdam neighbourhood/postcode service areas, and available time windows. Operators approve profiles. Customer matches use active provider catalog entries and require a published service area to cover the requested area. Matching uses area labels, not geocoding or distance claims. An uncovered area can be added to an operator-visible waitlist. The exact address is requested after professional selection, required for plan approval, and returned only in the customer's workspace and that assigned professional's workspace; it is redacted from evidence-review AI input. Published availability is optional so both parties can propose a visit. No fictional professional or seeded appointment is exposed through production routes.
- **Workflow:** request intake, assessment escalation, actual provider offers, total-price proposals/counter-offers with bilateral acceptance, customer quote approval, date proposals/counter-offers, agreed rescheduling, appointment reservation, work start, private uploads, professional completion notes (without a forced customer request), completion approval, scope-change proposal/approval and explicit PayPal payment steps are server-validated.
- **Scheduling and recovery:** availability rows are locked for booking, and a professional-level advisory lock prevents overlapping reservations across services. A selected slot stays reserved while the professional has two business hours to confirm (weekdays, 09:00–17:00 in the appointment display timezone; the Amsterdam-clock correction is still open); a decline or timeout releases it. A professional cancellation releases the visit and lets the customer reuse the request to find another professional. Customer cancellations at least 24 hours before a visit release it; later requests wait for operator review. Timestamps drive one-time 24-hour visit, evidence, completion-review, and payment-approval reminders, plus operator-queue escalation for stalled jobs.
- **AI providers:** Gemini, OpenAI, and Claude (Anthropic) implement a shared structured-generation contract for intake and customer-triggered evidence coverage. Set `AI_PROVIDER`, `AI_PROVIDER_KEY`, and `AI_MODEL` together. Provider keys remain server-side; model suggestions cannot set prices or advance payment state.
- **Cloudflare R2:** private S3-compatible uploads accept JPEG, PNG, WebP and PDF up to 10 MB. The API checks the selected request before upload and download; public bucket URLs are not used.
- **Authorization recovery:** booking-time and negotiated-date timing choices, exact-scope authorization reconciliation, callback replay, serialized timing deferral, and durable River hold release for decline/cancellation/confirmation expiry are implemented. Scope increases release the old hold and explicitly return the new total to after-completion authorization. Automatic expiry/fresh-approval handling remains open.
- **PayPal marketplace sandbox:** Professionals can complete PayPal before-payment onboarding; the server verifies referral tracking, seller payment/refund permissions, and current receivability. Orders v2 `AUTHORIZE` route to the verified professional, and explicit customer capture requests `INSTANT` seller disbursement. The payment operation is bound to that seller in PostgreSQL. Verified webhook events are deduplicated and processed asynchronously for seller onboarding/consent revocation, capture, denial, refund, reversal, and customer-dispute updates. Operator-approved full refunds use a persisted idempotency key. Partial refunds and payment reversals become reconciliation-only operator cases; they are never shown as completed full refunds. Marketplace identifiers are present in the ignored local app configuration, but their provider validity and a real sandbox seller/wallet journey remain unverified. No platform fee is applied; there is none for now (decided 17 October 2026).
- **Operator workspace:** professional applications can be approved or rejected after the recorded identity/business, PayPal onboarding, qualification, and insurance checks are complete. The queue includes late cancellations, customer-reported issues, PayPal reconciliation, stalled work, ambiguous intake, pending scope changes and missing documentation.
- **Verified job reviews:** after completion and captured payment, a customer can submit one 1–5 star rating and optional comment; the assigned professional can post one response. Unpaid, incomplete, and fully refunded jobs are ineligible. Both actions stay within the authenticated request workspace and enqueue a generic notification. Public profile aggregation and review moderation/reporting are not enabled until their visibility and policy are defined.
- **Dutch and English product UI:** the customer and professional task flows offer a persisted EN/NL preference, locale-aware date and currency formatting, translated intake, booking, agreement, cancellation, payment, review, and service-profile controls. Intake and evidence AI responses follow the language of the customer's request. Operator screens are translated too: server reasons arrive as codes, and a test checks operator strings against the Dutch catalogue; server error messages an operator can trigger still show in English. Native-language editorial review is still a launch QA item.
- **App packaging and request limits:** Vite builds the browser client, and Go serves the built files and API behind one origin. The Dockerfile produces a small non-root runtime image. Compose runs Caddy, the app, and persistent PostgreSQL. Authenticated reads, writes, and AI-backed requests use per-account token buckets. Deployments migrate separately before starting the app and River. Readiness includes a bounded database ping and is separate from liveness; see the README for the local and production commands.
- **No runtime preview controls:** the browser has no identity impersonation, demo scenarios, reset action, seeded profiles, placeholder evidence or simulated payment confirmation. Its workspace switch uses authorized memberships on one account and persists the preference. Deterministic fixtures remain in the workflow test source only.
- **Transactional notifications:** Important request, scheduling, payment, review, and operator-resolution events create a durable in-app notification for the intended account in the same transaction as the event. The inbox is scoped to the signed-in role/account, tracks read state, links directly to its request, and refreshes every 30 seconds while the browser is visible. River and a PostgreSQL outbox deliver corresponding generic updates through SMTP, retry failed deliveries, reclaim interrupted sends, and use stable Message-IDs. The operator queue shows aggregate failed, unconfigured, and stalled delivery counts without exposing recipient addresses or message content. SMTP delivery is at-least-once across a process-failure window; duplicate email is possible.

- **Customer request photos:** a customer can attach up to six JPEG/PNG/WebP photos of the problem. They are stored privately under a request-scoped key, recorded on the workspace, never sent to an AI provider, and readable only by the owning customer and, once chosen, the assigned professional. They are separate from completion evidence. Covered by the persisted HTTP journey.
- **Consumer policy publication and acknowledgment:** operators publish externally reviewed policy versions (`/api/operator/policies`); signed-in users read the current text (`/api/policies`). Customers acknowledge the version snapshotted with their booking before work starts, and can request a withdrawal review. The product ships no default legal text.
- **Operator Policies view and reason codes:** operators manage consumer policies and service evidence-policy reviews in one place. Stalled-job cases carry a reason code and responsible role so the reason reads in the operator's language. `npm run test:i18n` fails when an operator string lacks a Dutch entry.
- **Follow-up questions and support notes in the request:** the assistant's post-booking question, the professional's reply and the reviewable summary appear in the request, and notes our team sent to a participant appear as "Messages from our team".
- **Agent-managed requests (slices 1-4):** every customer and professional has an agent from their first message, with a default mandate they can change or pause in "Assistant preferences" (budget from the chat, days and hours, price floor, optional delegation of work approval; payment always stays with people). The customer's assistant converses in the chat: it asks for the address and availability, compares it with the professional's open times, asks whether a time suits, and books after a yes (see AGENT_ARCHITECTURE.md). The two agents choose a match, counter once on price, book, confirm and handle visit times through the same validated actions a person uses; whatever falls outside the mandate comes back as a question. Activity and open questions appear on the request page and as an app banner. Slice 2 adds agent steps for reschedules, declined visits and professional cancellations (late or paid changes stay with people and the operator) and emails the person when an agent asks a question, in Dutch or English. Slice 3 adds the professional's own private assistant chat (it asks before acting outside their settings and reports what it agreed), visit-time negotiation between the two agents, and reading of free-form replies: quick replies, yes/no and numbers are read locally, anything else goes once to the configured AI provider as untrusted text and comes back only as a sanitized intent, with the built-in English and Dutch parser as fallback. Slice 4 keeps the assistants in the conversation after booking (move or cancel the visit in free text, asking before approving finished work, the professional's assistant reporting approval and payment), gives them short bot names with a bot icon, and puts the assistant's open question first on the request page. When the workflow refuses a step an assistant tried, it says so in the chat, and a refused work approval names exactly which documentation is missing. Covered by `TestAgentsNegotiateBookAndEscalate`, the availability parser tests and the persisted agent journeys in `internal/httpapi/journey_test.go`. Design and limits: [AGENT_ARCHITECTURE.md](AGENT_ARCHITECTURE.md).

## Not implemented or not ready for live production

- **Marketplace release readiness:** seller onboarding, professional-directed instant settlement, seller-scoped refunds and onboarding webhooks are implemented for sandbox. Customers can authorize during booking or wait until after completion approval, which is the default; before the booking-time authorization succeeds, they can switch to the later path. Booking-time authorization blocks professional confirmation, and capture remains separately gated. The platform merchant ID, partner attribution code and webhook ID are present in ignored local configuration; their provider validity and actual sandbox routing have not been verified. Live merchant validation, authorization expiry/reauthorization and target currency settlement are not implemented or confirmed. There is no platform fee for now (decided 17 October 2026). PayPal partner approval and settlement confirmation remain external release gates.
- **Refund limits:** the operator tool initiates full refunds only. Partial refunds made outside the application and payment reversals require an operator to reconcile the PayPal account before closing the case. No automatic second refund is offered for those cases.
- **Consumer policy:** statutory withdrawal, work-start acknowledgement, category-specific qualification requirements, and approved Dutch/EU cancellation and refund terms still need policy and legal review. The application does not infer urgent-service exceptions.
- **Notifications:** email requires production SMTP configuration (`SMTP_ADDR`, `SMTP_FROM`, and optional paired username/password). Provider bounce telemetry, sender-domain authentication and live delivery checks still need setup; no operator email roster is configured. SMS and WhatsApp are not implemented. SSE and push updates are not implemented; visible workspaces refresh every five seconds and offer manual refresh.
- **Scheduling limits:** travel buffers and external calendar integration are not implemented. Weekly working hours with time between visits, days off and removable free times are implemented. The intended confirmation clock is two business hours on weekdays 09:00–17:00 Europe/Amsterdam; the implementation still uses the appointment display timezone.
- **Directory quality:** area filtering currently compares provider-published labels and postcode prefixes. No geocoder, postcode/address validation service, map, travel-time routing or coverage polygons are configured. Area matching is not distance ranking.
- **Operational controls:** the public sign-in start and callback use short-lived, in-memory per-client limits; broader edge-level abuse protection and a shared limiter before adding API replicas remain deployment work. A local PostgreSQL dump was restored into an isolated database and its 14 migrations and notification tables verified on 13 October 2026. Off-host backups, scheduled recovery drills, account recovery policy, retention/deletion workflows, malware scanning, security monitoring and incident runbooks still need operational setup.
- **Second frontend redesign:** the design approved on 17 October 2026 ([DESIGN_SYSTEM.md](DESIGN_SYSTEM.md); the original handoff and board export were removed) replaces the 14 October interface: tokens and self-hosted Bricolage Grotesque/Instrument Sans, shell, six-step journey, customer, professional, operator and public screens. Type sizes were set to product density on 17 October (14 px body, 40 px controls on desktop, 44 px on phones) and composers use one border without a halo. Dutch strings for the new copy are drafts that still need native review. Authenticated pages were checked in a browser for the customer flow, and on 18 October the customer and professional assistant chat were exercised live with the real AI provider; operator screens and live payment steps still need a pass with real data.
- **Agent limits:** agent bookings always pay after completion, because an autonomous PayPal hold needs a saved payment method and spending authorization that are not set up; payment is never delegated (approving finished work can be, by the customer, in the preferences); escalations are emailed and shown in the app but not pushed; late cancellations, paid changes and refunds stay with people and the operator. See [AGENT_ARCHITECTURE.md](AGENT_ARCHITECTURE.md).
- **Local multi-account verification:** browser tests against two independent Auth0 accounts require a configured `DATABASE_URL`, Auth0 tenant and provider setup. Use separate browser profiles/sessions; do not reintroduce a role switcher for tests.

## Configuration and mode behavior

There is no `APP_MODE=demo`. `APP_ENV` is `development` or `production`. AI provider selection supports Gemini, OpenAI, and Claude (Anthropic); unsupported providers fail startup. The runtime requires a configured AI provider, private R2 and PayPal credentials. Auth0/PostgreSQL may be absent only in local development, in which case sign-in and account workspaces are unavailable. Production startup fails fast when database, OIDC or built frontend settings are missing.

The root `.env` is ignored by Git. Choose a model ID supported by the selected provider and set it in `AI_MODEL`; `AI_PROVIDER_KEY` contains the selected provider's server-side key and is never sent to the browser or logged by the app. Production configuration also requires `PAYPAL_WEBHOOK_ID`, `SMTP_ADDR`, and `SMTP_FROM`; configure a webhook on the PayPal app used by the sandbox credentials and subscribe it to the event types in [PAYMENTS.md](PAYMENTS.md).

## Flow verification

The 17 October `make check-flow` run passed. The gate includes frontend controller tests, Svelte diagnostics and production build, Go tests/vet/production build, five deployment/publication tests, and workflow transitions through the production HTTP handlers, PostgreSQL persistence, opaque sessions and PayPal adapter. It covers account isolation, slot conflicts and expiry, professional cancellation/rebooking, late cancellation review, reminder scheduling, payment recovery, webhook deduplication, partial-refund handling, stable refund request IDs, and a verified customer review with professional response. Five persisted HTTP journeys cover both timing choices, both negotiated-date directions, restart/reconciliation, callback replay, and cancellation with late callback and River hold release. Provider/database regressions cover exact-attempt claims, in-flight uncertainty, timing switching, expiry/operator cancellation and separate capture approvals. CI and publication are configured to run the complete gate. External services are deterministic contract fixtures. Live Auth0, provider connectivity, SMTP delivery and PayPal wallet approval are separate checks and must not be reported as proved by contract fixtures.

## Current release decision

The account/workspace boundaries and routine cancellation, dispute, payment-reconciliation and notification workflows are implemented. The product is not ready to accept live funds: PayPal remains sandbox-only, and partner approval, seller payout configuration, settlement, consumer policy, and production provider configuration remain release blockers.
