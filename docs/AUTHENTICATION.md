# Authentication and account routing

## Implemented identity flow

Auth0 Universal Login authenticates users. The Go API performs the OIDC authorization-code exchange using PKCE, validates issuer/audience/signature/expiry plus `state` and `nonce`, and stores an opaque random session token as a hash in PostgreSQL. The browser receives only an HttpOnly session cookie. Production cookies are Secure and use SameSite=Lax. Unsafe same-origin API requests validate the `Origin` header.

Login starts on `APP_BASE_URL` before setting cookies. Local aliases such as `127.0.0.1:8090` redirect to `localhost:8090`, so the login and callback share a browser cookie host. Each login attempt has its own short-lived HttpOnly state cookie, allowing separate tabs to sign in without overwriting each other. PostgreSQL consumes each transaction once. A failed or expired callback returns to the welcome page with a safe retry message; codes, state values and tokens are never echoed in that redirect or diagnostic logs.

Start sign-in from the app in the browser where you intend to finish it. A callback URL is a one-time response, not a shareable login link; opening it in another browser does not carry the original browser cookie.

SamenKlaar identifies a person by the verified `(issuer, subject)` pair, not email. PostgreSQL owns customer, professional and operator memberships. First login creates active customer access. Professional onboarding adds a pending professional membership to that same identity. Operator membership must be provisioned by the service owner. Switching workspaces requires an existing authorized membership and atomically updates the current session and `accounts.preferred_role`. New logins restore this account preference; revoked preferences fall back to customer access.

Customers own request workspaces. A professional can read or update a job only when that request's server-stored professional account ID matches their active account. Evidence, state changes and PayPal endpoints use the same request-level ownership checks. Client-supplied actor values are overwritten by the session role.

Session endpoints:

- `GET /api/auth/login` starts the single Universal Login flow. Legacy `role` parameters do not request or grant a role.
- `GET /api/auth/callback` validates the response and creates a SamenKlaar session.
- `GET /api/auth/session` returns the authenticated account, active role and memberships.
- `POST /api/auth/role` switches to an existing membership and persists the workspace preference.
- `POST /api/professional/onboarding` lets a customer add pending professional access to their existing account and open its onboarding form.
- `POST /api/auth/logout` deletes the SamenKlaar session and redirects through Auth0 logout.

Operator endpoints require a provisioned, active operator membership. There is no browser-controlled role grant.

## Auth0 setup

Create a Regular Web Application in Auth0. For local development, register:

- Allowed callback: `http://localhost:8090/api/auth/callback`
- Allowed logout URL: `http://localhost:8090`
- Allowed web origin: `http://localhost:8090`

**Application Login URI** is the app's login initiation route:
`https://YOUR_APP_DOMAIN/api/auth/login`. This existing route starts a fresh
authorization request and redirects to the configured Auth0 tenant's
`/authorize` endpoint. It is separate from the callback URL, which receives
Auth0's response at `/api/auth/callback`.

Leave Application Login URI blank for the localhost setup. Auth0 requires HTTPS
and does not accept localhost for this field; local allowed callback/logout URLs
still use the app's local origin. See [Auth0's default login route documentation](https://auth0.com/docs/authenticate/login/auth0-universal-login/configure-default-login-routes).

Run `make init-local`, then set these variables in `.secrets/local/app.env`:

```dotenv
APP_BASE_URL=http://localhost:8090
AUTH0_ISSUER_URL=https://YOUR_TENANT.eu.auth0.com/
AUTH0_CLIENT_ID=...
AUTH0_CLIENT_SECRET=...
AUTH0_REDIRECT_URI=http://localhost:8090/api/auth/callback
# DATABASE_URL is generated by make init-local for the private DB container.
```

Use the exact issuer URL from the Auth0 tenant. The `AUTH0_` prefix identifies the credential provider; OIDC remains the authentication protocol. Update existing environment files and external deployment configuration to these names before deploying; the app reads only the provider-specific keys.

For production, use the public HTTPS app origin and register its exact callback and logout URLs. Do not reuse the local callback. Run `make deploy-local` or `make deploy-prod` to migrate and start the complete stack; no separate frontend server is needed.

To provision an operator, have that person sign in normally first so the verified `accounts` row exists. A service owner then grants an active operator membership directly in PostgreSQL. The UI does not expose an operator self-service login or role grant. Match both issuer and subject exactly; never grant based on an email supplied by the browser:

```sql
INSERT INTO account_memberships (account_id, role, status)
SELECT id, 'operator', 'active'
FROM accounts
WHERE issuer = 'https://YOUR_TENANT.eu.auth0.com/'
  AND subject = 'AUTH0_SUBJECT'
ON CONFLICT (account_id, role) DO UPDATE SET status = 'active', updated_at = now();
```

## Account-isolation checks

Use different Auth0 users in separate browser profiles (or isolated browser contexts). Verify that customer A cannot load customer B's workspace or evidence by changing a workspace ID, and that a professional cannot access a job assigned to another professional account. A professional profile must be approved before the directory publishes it. Test logout and session expiry in both browser profiles.

The browser must not persist identity-provider access or refresh tokens in localStorage. The workspace switch changes authorized roles for one verified identity; it cannot impersonate another account. Own-service bookings are excluded and rejected at the server and transaction boundaries. Development without Auth0/PostgreSQL intentionally has no account sign-in path.

## Production follow-up

Before exposing accounts publicly, configure tenant email verification, MFA policy, brute-force protections, account recovery, session revocation/rotation, secret rotation and monitoring. Use the deployment's HTTPS origin and secure cookie settings. Restrict access to operator provisioning and audit those changes. Confirm Auth0 tenant entitlements directly before launch.

## Customize the hosted Auth0 login page

Use Auth0 Universal Login's no-code theme editor to match SamenKlaar. This is a tenant dashboard setting; editing the Svelte welcome page does not publish a hosted Auth0 theme.

1. In Auth0 Dashboard, open **Branding → Universal Login → Customization Options**.
2. Use the following values in its Styles panels, then **Save and Publish**.
3. Under **Advanced Options → Custom Text**, set the login screen title to **Welcome to SamenKlaar** and description to **Sign in to find help and keep your bookings together.**
4. Use **Try** in the theme editor to preview a new login.

| Element | SamenKlaar value |
| --- | --- |
| Page background | `#f7f8fa` |
| Widget background | `#ffffff` |
| Primary button and links | `#153b88` |
| Primary button text | `#ffffff` |
| Heading | `#171c26` |
| Body text | `#171c26` |
| Widget/input border | `#e1e5ed` |
| Focus color | `#5281db` |
| Button/input radius | 6 px |
| Widget corner radius | 8 px |

A matching SVG logo is supplied at [`public/samenklaar-logo.svg`](../public/samenklaar-logo.svg) and packaged into the app as `/samenklaar-logo.svg`. Auth0's **Widget → Logo URL** needs a public HTTPS URL, such as `https://YOUR_APP_DOMAIN/samenklaar-logo.svg` once the app has an HTTPS deployment. The local asset can be previewed at `http://localhost:8090/samenklaar-logo.svg`.

Use the theme editor and text customization for the app. Full page templates support additional layout customization and require an Auth0 custom domain. Application credentials are not Auth0 Management API credentials and cannot publish tenant branding by themselves.

References: [Theme editor](https://auth0.com/docs/customize/login-pages/universal-login/customize-themes), [Custom text](https://support.auth0.com/center/s/article/universal-login-page-customization-text-prompts), [Page templates](https://support.auth0.com/center/s/article/universal-login-page-customization-page-templates).
