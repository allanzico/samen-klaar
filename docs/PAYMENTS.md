The platform merchant ID, partner attribution ID, and webhook ID are present in the ignored local app configuration. Each professional completes PayPal's before-payment onboarding before accepting a paid booking. The server verifies the returned seller merchant ID against the referral tracking ID, confirms the seller can receive payments and has granted the required payment/refund permissions, and stores that verified seller against the professional account. Callback query parameters alone never mark a seller eligible. Revoking consent disables new payment actions.

At booking, customers can choose when to authorize the agreed amount: during booking, or after they review and approve the completed work. After the work is the default and is preselected (decided 17 October 2026). Before a booking-time authorization succeeds, they may switch to the after-completion path. Both paths create an Orders v2 order with `intent=AUTHORIZE` and the verified professional as `purchase_units[].payee`; the customer approves at PayPal and Go authorizes the order. A booking-time authorization must succeed before the professional can confirm the visit. It places a temporary hold, not a capture. Completion approval and payment approval remain separate customer actions, and only then can Go capture the exact current-scope amount with `payment_instruction.disbursement_mode=INSTANT`, routing the captured payment to that professional. PayPal says an authorization lasts up to 29 days and recommends capture within its initial 3-day honor period; after that, success depends on risk and funds availability. If a booking-time authorization cannot be used later, the customer must approve a new payment authorization. PayPal settles the seller payment; SamenKlaar does not hold funds as escrow. This uses PayPal's marketplace checkout and seller disbursement behavior, not PayPal's separate batch Payouts API. See [PayPal's authorization and honor period](https://developer.paypal.com/payment-methods/auth-honor/) and [authorize and delay capture](https://developer.paypal.com/checkout/delay-capture/).

No platform fee for now (decided 17 October 2026): none is charged, shown or sent to PayPal. A later fee needs a rate, disclosure before booking and PayPal `PARTNER_FEE` entitlement; do not invent a rate.

The amount, authorization ID and capture state are server-owned. Go validates the current job and scope before each operation and uses stable `PayPal-Request-Id` values. Order, authorization and capture records are stored in PostgreSQL with conditional state claims; API instances coordinate through persisted state instead of relying on process memory. If an operation is uncertain after a timeout or restart, the customer can ask SamenKlaar to reconcile with PayPal before another action. An active authorization is voided before a customer-approved scope change proceeds.

### Recovery and release

A lost authorization response can be reconciled after restart. The adapter checks the provider order/reference, amount, currency, seller and authorization against the durable operation; HTTP and PostgreSQL then record the verified authorization for the current scope. Replaying the callback does not create another hold or timeline event. A temporary failure to save the booking marker leaves the authorization available for reconciliation.

Changing to after-completion timing locks the workspace and payment operation together. A created, unsubmitted authorization order can be abandoned as `deferred`. Creating, authorizing, uncertain, authorized and releasing operations block the switch until their status is resolved. A late callback for an abandoned order cannot authorize it. Checkout at completion creates a fresh request identity for the approved total.

Decline, ordinary cancellation, operator-approved late cancellation and confirmation expiry commit release work with the reservation change. River retries the exact stored attempt, including recovery of an uncertain authorization, then voids with its original `PayPal-Request-Id`. A lost void response is reconciled/retried without replacing the request identity. A stale release cannot void a replacement order. Rebooking waits for pending release work to settle; capture is never a release-worker action. See [PayPal Payments v2](https://developer.paypal.com/api/payments/v2) and [PayPal idempotency](https://developer.paypal.com/api/rest/reference/idempotency/).

The timing choice also applies when both parties negotiate a visit. Selecting early authorization holds the agreed visit pending customer authorization and professional confirmation. Scope increases during work explicitly use after-completion authorization for the revised total, after releasing any previous hold. Authorization expiry is detected and the customer can give a fresh approval for the same amount and seller; neither closes the provider-readiness gate below.

Every payment action is associated with a job and request workspace. The PayPal return URL carries that workspace ID so multi-request accounts return to the correct job. A workspace ID is not treated as authorization: Go checks customer ownership on each route.

## Why this is not live-payment ready

The PayPal adapter is still sandbox-only. A browser redirect is not proof of capture: the return path checks with PayPal, while the public webhook route verifies each transmission with PayPal before durably queueing a deduplicated event. PostgreSQL/River process capture, denial, refund, reversal and customer-dispute events asynchronously. A capture can succeed at PayPal while a database outage delays local state; stable operation records and reconciliation remain available for recovery.

The application now has marketplace seller onboarding, seller-bound orders, instant professional settlement on capture, seller-scoped refunds, and onboarding/revocation webhook handling. Provider-contract tests cover these paths, and a real sandbox buyer and seller were taken through them by hand (see Verification). The operator tool supports full refunds with a stable idempotency key. A partial refund or payment reversal reported by PayPal is held in a reconciliation-only operator case; it cannot be mistaken for a completed full refund or trigger another automatic refund. Partner fees, deposits, live authorization expiry and reauthorization remain unimplemented or undecided.

Keep `PAYPAL_ENV=sandbox`. Do not connect live credentials or accept customer money until the external marketplace, policy and production-readiness requirements below are satisfied.

## Configuration

Set these values in the ignored project `.env` or the production secret manager:

```dotenv
PAYMENT_PROVIDER=paypal_sandbox
PAYPAL_ENV=sandbox
PAYPAL_CLIENT_ID=...
PAYPAL_CLIENT_SECRET=...
PAYPAL_WEBHOOK_ID=...
PAYPAL_PLATFORM_MERCHANT_ID=...
PAYPAL_PARTNER_ATTRIBUTION_ID=...
```

Use the sandbox Platform REST app credentials, the platform business account's PayPal merchant ID, and the PayPal partner attribution (BN) code associated with the platform. Configure the webhook on that same sandbox app, then set its ID in `PAYPAL_WEBHOOK_ID`. Subscribe to `MERCHANT.ONBOARDING.COMPLETED`, `MERCHANT.PARTNER-CONSENT.REVOKED`, `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.DENIED`, `PAYMENT.CAPTURE.REFUNDED`, `PAYMENT.CAPTURE.REVERSED`, `CUSTOMER.DISPUTE.CREATED`, `CUSTOMER.DISPUTE.UPDATED`, and `CUSTOMER.DISPUTE.RESOLVED`. Set the callback URL to `https://<app-domain>/api/paypal/webhook`; the endpoint acknowledges only after verification and queue persistence. Keep the webhook ID in `PAYPAL_WEBHOOK_ID`.

### Personal accounts, business accounts and sandbox logins (20 October 2026)

Customers pay through checkout with their own PayPal account. They do not connect a professional receiving account, grant the seller permissions or create a company account to pay. The professional connection is for receiving payment for work; an existing eligible PayPal account can be connected by choosing Log in on the PayPal page.

PayPal documents personal-account support for casual sellers in the Netherlands when onboarding **before payment with PayPal Checkout**. This is the `EXPRESS_CHECKOUT` product already requested by the adapter. Expanded Checkout and onboarding after payment have different requirements and are not a workaround for this flow. Account/country eligibility and PayPal identity checks still apply. Casual sellers do not support card acceptance, and alternative payment methods require a business account; do not promise those payment methods to personal-account sellers.
